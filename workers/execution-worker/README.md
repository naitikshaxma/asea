# Execution Worker Boundary & Sandbox Architecture

## 1. System Boundary and Security Model

The Execution Worker is the runtime subsystem responsible for executing tests, linting, reproduction scripts, and speculative code patches generated by AI models.

**In Phase 1, arbitrary shell execution is strictly disabled.** No endpoint or module in this codebase permits unbounded system command execution on the host machine.

The execution boundary is documented here to establish zero-trust architecture invariants prior to Phase 2 activation.

## 2. Core Security Invariants

### 2.1 Disposable Sandboxes
- **Lifecycle**: Every execution run (e.g. running a test suite or applying a patch) is provisioned inside a brand new, ephemeral container or microVM.
- **Teardown**: The sandbox container filesystem is destroyed upon job completion. No state persists between runs.
- **Runtime Target**: OCI runtime using `runsc` (Google gVisor user-space kernel) or AWS Firecracker microVMs.

### 2.2 Resource Limits (Cgroups v2)
Every sandbox process tree is constrained by strict Linux control groups:
- `cpu.max`: 200000 100000 (Maximum 2 CPU cores).
- `memory.max`: 2147483648 (Maximum 2 GB RAM). OOM killer terminates the sandbox immediately if breached.
- `pids.max`: 100 (Prevents fork bombs).
- Disk quota: 1 GB ephemeral tmpfs limit.

### 2.3 Network Restrictions
- Worker containers execute inside an isolated Linux network namespace (`netns`).
- Egress is disabled by default (`iptables -P OUTPUT DROP`).
- Egress allowlisting (if package installation is needed) is strictly confined to trusted package registries (e.g. `registry.npmjs.org`, `pypi.org`) through an egress proxy with TLS inspection.
- Access to private cloud metadata (`169.254.169.254`), internal Docker networks, and internal PostgreSQL/Redis instances is completely blocked at the network interface layer.

### 2.4 Least Privilege
- The container executes as an unprivileged user (`UID 10001`).
- All Linux capabilities (`CAP_*`) are dropped (`--cap-drop=ALL`).
- `no-new-privileges` flag is set to prevent setuid elevation.
- Seccomp filter blocks hazardous syscalls (`ptrace`, `bpf`, `mount`, `reboot`, `kexec_load`).

### 2.5 Controlled Credentials
- Host credentials, production tokens, and API secret keys are **never** mounted or passed as environment variables into the sandbox.
- When Git repository access is required, the worker receives a scoped, short-lived (15-minute) installation token with read-only permissions for the target repository.
- Sensitive environment patterns in execution logs are masked using real-time regex filtering.

### 2.6 Execution Audit Trails
- stdout and stderr are ingested as streaming event buffers with maximum byte ceilings (e.g. 10MB per run).
- Every executed command, exit code, CPU time consumed, memory high-water mark, and network connection attempt is recorded in structured JSON audit logs for human review.

## 3. Phase 2 Implementation Plan

1. **Worker Daemon**: Build a Go/Rust or Node worker agent listening to Redis task queues.
2. **Container Engine Adapter**: Implement the Docker/Podman/gVisor runner interface.
3. **Telemetry Collector**: Stream real-time sandbox execution logs to the API and web frontend.
4. **Verification Loop**: Run tests -> capture stack traces -> feed results back to the AI agent service.
